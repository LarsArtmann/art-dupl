go-finding — Adoption & Utilization Audit

art-dupl consumes go-finding as its findings interchange layer: a public adapter (printer/finding) and a self-registering BuildFlow provider (pkg/provider). The core interchange is used well, but several high-leverage capabilities the library already ships sit unused, and one of them waits on a parked branch that must be re-landed (rev 2: the branch is red on its own pins).

00Summary

The integration is deliberate, well-documented, and architecturally clean: go-finding is a consumer-side output layer, never the internal clone representation (ADR-0025). The GroupID contract, clone-of related links, the art-dupl/ metadata namespace, confidence clamping, and toolsdk self-registration are all used correctly. That is roughly 60% of the applicable surface done right.

The other 40% is where the value sits. The single biggest finding: the provider declares a fixed threshold contract because the toolsdk options channel did not exist when it was written — it exists now (toolsdk v1.14.0 is already fork's pinned dependency), the wiring is prototyped on feat/provider-threshold-knob — which is red on its own pins (rev 2 correction: the branch pins toolsdk v1.13.1 while its tests use v1.14.0 APIs, so it must be cherry-picked onto fork and re-gated, not fast-forwarded) — and TODO_LIST D1 is the only thing standing between the repo and a configurable knob. Two more high-value gaps: findings are constructed with the unvalidated NewFinding instead of the recommended Builder, and the go-finding ToLSP path — already exercised in tests — is never emitted by any CLI format.

The bottom line art-dupl treats go-finding as a wire format and stops there. It is leaving the library's validation, tuning (options channel), LSP surface, and report algebra (merge/diff/correlate) on the table. The threshold knob is the highest-impact, lowest-effort fix and is unblocked today.

◆What's already excellent

The adapter is a model of restraint: it models only what go-finding models, defers presentation heuristics to the CLI, and pins the decisions with tests.

+
Deterministic GroupID contract GroupIDOf maps a clone group to its content hash; the SARIF printer emits the same value as the go-finding/groupId property and the JSON clone_groups[].hash. Round-trip pinned by tests. (printer/finding/finding.go:75)
+
Related links built without quadratic regeneration findingIDs precomputes sibling IDs once, then relatedOf links each occurrence to the rest via RelationCloneOf. (printer/finding/finding.go:110)
+
Correct metadata namespacing Clone classification rides the art-dupl/* metadata namespace; the reserved go-finding/ prefix is respected. Zero-value keys are stripped in the SDK path.
+
Confidence, category, and detector contracts used properly Confidence(...).Clamp(), CategoryDuplication, the Detector interface, and toolsdk self-registration (toolsdk.Register) are all idiomatic.
+
Severity ladder shared with SARIF severityFor mirrors the SARIF printer's level ladder, so both output paths agree on the same group. The provider then caps advisory severity so detector-only findings cannot fail an error-gated pipeline.

Missed Opportunity · High impact

The toolsdk options channel is unused — the provider's threshold contract is frozen

pkg/provider/provider.go:70-85 · TODO_LIST D1 · branch feat/provider-threshold-knob

go-finding's toolsdk now supports declarative, per-run tunables: Spec.Options []Option plus WithOptions / OptionsFromContext and Spec.ValidateOptions (shipped in toolsdk v1.14.0 — the version already pinned in go.mod). art-dupl's provider declares no options and documents a deliberately fixed contract: "semantic mode, threshold 5 statements (not configurable via the SDK)." That was the correct call when there was no options channel; it is now a self-imposed limit. The wiring already exists on feat/provider-threshold-knob (declares a threshold int option, kind-checked, range-validated 1–1000). Rev 2 correction: the branch is not green — its own go.mod pins toolsdk v1.13.1 (predating the options channel) while its tests call Spec.ValidateOptions / OptionValues (v1.14.0+), so it does not compile standalone. It is exactly one commit ahead of fork; landing = cherry-pick onto fork's pins + full re-gate.

Fix: re-land the parked branch (cherry-pick, not fast-forward) Fork's dependency is satisfied (toolsdk v1.14.0); the branch's own pin is not. Cherry-pick bb8b925e onto fork, keep fork's go.mod/go.sum on conflict, re-gate; then have BuildFlow map consumer config to toolsdk.WithOptions. 
// pkg/provider/provider.go — on feat/provider-threshold-knob
Options: []toolsdk.Option{{
    Name:        "threshold",
    Kind:        toolsdk.OptionKindInt,
    Default:     5,
    Description: "Minimum clone size (statements) to report",
}},
// and in Detect:
if v, ok := toolsdk.OptionsFromContext(ctx); ok {
    if t, ok := v["threshold"].(int); ok {
        opts.Threshold = t
    }
}
Anti-Pattern · Medium impact

Findings are built unvalidated, bypassing go-finding's own validation layer

printer/finding/finding.go:137 · 2 call sites

The adapter constructs findings with the low-level NewFinding, which the go-finding README explicitly documents as skipping validation, and recommends Builder for all new code. art-dupl never calls Finding.Validate() in production — the only Validate() call is Report.Validate() inside a test. The malformed-finding classes go-finding's validators would catch (empty rule, invalid tags, mis-shaped ranges) are therefore unguarded at the boundary; today the adapter happens to produce valid output, but nothing enforces it.

Fix: construct via the Builder (or validate before emit) The Builder gives compile-time branded types (RuleName, ToolName) plus construction-time validation; a Template can stamp the shared tool/category/fix-strategy once across every group. 
// Before
f := gofinding.NewFinding(rule, tool, msg, sev, pos, conf)

// After — validated, fluent
f, err := gofinding.NewBuilder(
    gofinding.RuleName(RuleCloneDetected),
    gofinding.ToolName(ToolName),
    msg, sev, pos,
).
    WithGroupID(GroupIDOf(group)).
    WithRange(rangeOf(cl)).
    WithSnippet(cl.Fragment).
    Build()
Missed Opportunity · Medium impact

The LSP diagnostic surface is tested but never emitted

config/output_format.go:8-14 · no OutputFormatLSP

go-finding ships first-class LSP diagnostics (Finding.ToLSP()) with GroupID round-tripping through diagnostic data. art-dupl exercises this in tests (gofinding.FromLSP) but the CLI's OutputFormat enum has no LSP (or go-finding-JSON) member, so an editor-facing consumer has no way to get diagnostics from art-dupl directly. The adapter is described in SDK_DESIGN as "adapter as public library API, SARIF as the wire" — but LSP is the one wire go-finding already provides and art-dupl leaves unused.

Fix: add a finding/LSP output format Add OutputFormatLSP (and optionally OutputFormatFinding). Rev 2 correction: ToLSP() is a per-Finding method (func (f Finding) ToLSP() LSPDiagnostic) — there is no Report-level LSP export. The printer iterates findings via Report.FindingsSnapshot() and calls f.ToLSP() on each; the adapter already builds the findings; only the printer and the enum are missing. 
report := finding.ToReport(groups, opts) // already exists
for _, f := range report.FindingsSnapshot() {
    d := f.ToLSP() // per-finding: LSPDiagnostic, GroupID in Data
    _ = d          // one diagnostic per clone occurrence
}
Missed Opportunity · Medium impact

Accept directives are filtered in-process but never surfaced as suppressions

cmd/accept_directive.go · printer/sarif.go (no suppressions array)

go-finding models suppression at the finding level (Finding.Suppression with in-source/in-config/in-review kinds, rule, reason, and optional expiry), and its SARIF export/import round-trips a suppressions array. art-dupl has an equivalent concept — the //art-dupl:accept directive — but it is resolved by dropping groups before output. A downstream tool (or a code-scanning UI) therefore cannot tell "clean" from "accepted": the acceptance is invisible on the wire.

Fix: emit accepted groups as suppressed findings Map AcceptedSet matches to Suppression{Kind: SuppressionInSource, Rule: ...} and keep them in the report, so SARIF consumers see the suppression rather than an absence. Rev 2 correction: go-finding's SARIF export drops suppressed findings by default — they survive the round-trip only via ToSARIFWithOpts(WithIncludeSuppressed()); the opt-in path must test through that option.
Partially Used · Medium impact

Report algebra (merge / diff / correlate) is reinvented as the baseline package

baseline/baseline.go · go-finding merge.go, diff.go, correlate.go

go-finding ships Combine (with dedup), Diff (added/removed/modified/unchanged by finding ID), and Correlate (relationship scoring). art-dupl's baseline/check feature hand-rolls its own persisted hash set and comparison because it predates go-finding and works at clone-group granularity. That is defendable — the baseline is human-curated and intentionally not a finding diff — but the duplication is real: two notions of "what changed since last run" now coexist, and cross-report correlation (which go-finding provides) is simply absent.

Fix: choose one owner for "changed since" Keep the human-curated baseline as the gate, but expose a Report-level diff (via Diff) for machine consumers so the finding model has one comparison semantic.
Missed Opportunity · Medium impact

Report coverage evidence is not populated

pkg/provider/provider.go:151 · go-finding report.go:71-78

go-finding's Summary now has FilesScanned (always serialized, so "scanned 0" is provable coverage) and SkippedModules (nested go.mod boundaries a tool deliberately skipped). art-dupl analyzes a file set and knows exactly how many files it scanned and which nested modules it excluded for monorepos, but the SDK interchange path reports findings only — the coverage claim is invisible. FilesScanned first appears in core v1.14.0, so this is coupled to the version bump below. Rev 2 correction: this is upstream-gated — the toolsdk Detector contract is Detect(ctx) ([]Finding, error); art-dupl has no channel to set Report.Summary, so populating it requires a go-finding toolsdk change first, then a tag, then consumption.

Fix: upstream coverage channel, then populate Prototype a toolsdk coverage channel in go-finding (Spec field or Detect-result extension), PR → tag → consume; then set Summary.FilesScanned / SkippedModules so consumers can distinguish "no clones" from "not analyzed". Not achievable from art-dupl alone.
Partially Used · Medium impact

SARIF is hand-rolled instead of exported through go-finding

printer/sarif.go · go-finding sarif_export.go

go-finding exports SARIF (Report.ToSARIF) and round-trips its own output. art-dupl maintains an independent SARIF emitter and only imports go-finding's FindingsFromSARIF in tests. The reason is legitimate — art-dupl's SARIF carries rule metadata and properties the generic exporter does not — but it means the SARIF wire is the one place where art-dupl and its own adapter can drift, and the go-finding/groupId property is emitted by hand rather than by the library that defines it.

Fix: cross-check, don't replace Keep the custom emitter, but add a test asserting report.ToSARIF() and printer/sarif.go agree on group identity and severity for the same input — the single-source-of-truth check the current suite lacks.
Partially Used · Low impact

Tags carry only the severity downgrade, not clone semantics

pkg/provider/provider.go:180 · pending status item #47

go-finding's Tags are a validated, lowercase-hyphenated classification channel. art-dupl uses exactly one tag (original-severity-*) and pushes clone type, category, and priority into metadata strings instead. Type-1/Type-2/Type-3 and duplicate are natural tags; a consumer that filters or groups on tags cannot see them today.

Fix: add validated semantic tags alongside metadata f.Tags = append(f.Tags, gofinding.Tag("type-"+typeNum)) — tags for routing, metadata for detail.
Partially Used · Low impact

Position column is left unset

printer/finding/finding.go:182-188

positionOf sets File, Line, and byte Offset but omits Column. go-finding's Position supports a 1-based column and its Range/overlap helpers use it. Findings are lsp-compatible without it, but any column-precise consumer gets 0.

Fix: thread the start column from the clone When the parser has it, set Column the way the --dump-tokens position table already computes line:col.

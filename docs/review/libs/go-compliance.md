## Fit analysis

### Does art-dupl need a compliance/policy surface?

Not as a consumer today. go-compliance's design intent is that BuildFlow-covered projects need zero integration (README §Architecture), and art-dupl is maximally BuildFlow-integrated (self-registering toolsdk provider at pkg/provider/provider.go:87, Live since 2026-09-25 per the toolsdk report). Its compliance story is already carried by: the CI gate table in AGENTS.md (nine workflows incl. Architecture Lint and Clone Detection), the monthly self-scan ledger (AGENTS.md, scripts/self-scan.sh, docs/SELF_CLEAN_LEDGER.md), and the committed baseline ratchet (`.art-dupl-baseline.json`, `.github/workflows/art-dupl-check.yml:1`).

### Is there an argument the local gates would be BETTER as compliance rules in a fleet hub?

No — the argument runs the other way on all three guards:

1. **jsonv2gate** (`internal/jsonv2gate/jsonv2gate_test.go`): it encodes a hard invariant (v1-only marshaling for Duration-bearing wire paths) learned from three live production breakages (AGENTS.md jsonv2 paragraph). Its value is _failing the build before push_, with an allowlist and AST-level precision a generic hub rule cannot express. As a hub "compliance rule" it would be an unactionable red cell after the damage was done.
2. **arch-lint** (`.go-arch-lint.yml`): the SDK type-independence boundary (zero `config/`/`errors/` imports in pkg/artdupl, enforced per AGENTS.md) is repo-structural; go-arch-lint fails locally and in CI. A hub rule would at best mirror the same verdict with worse latency and no diff context.
3. **Banned-linter guard** (`scripts/check-disabled-linters.sh:22` + `.github/workflows/lint-config-guard.yml:1`): exists precisely because an _external_ actor (the auto-committer) re-enabled banned linters — the guard must fire at the commit boundary, which a fleet dashboard cannot do.

The correct fleet division: go-compliance aggregates _outcomes_ (gate findings, evidence windows — it already ingests BuildFlow compliance JSON and art-dupl's dupl-gate verdicts, go-compliance/FEATURES.md:59); art-dupl owns _enforcement_. Art-dupl's gates feed compliance; they are not compliance rules.

## Fleet argument

go-compliance is the strongest centralization play in this batch at the _fleet_ level: one state model, one frozen wire contract, adapters instead of per-project plumbing, and it already closes the loop with art-dupl (dupl-gate consumes the pinned art-dupl binary; go-compliance/FEATURES.md:59). But the audit question is adoption **into art-dupl**, and there the fleet argument inverts: art-dupl's local machinery (arch-lint, jsonv2gate, lint guard, baseline ratchet, self-scan ledger) is enforcement-grade and repo-precise, exactly what a fleet hub cannot be. Re-implementing those guards as hub rules would multiply their failure modes rather than deduplicate them — they are not duplicated code in the first place; each encodes a repo-specific invariant. The genuinely shared thing — "does every repo pass its gates" — is already centralized on the BuildFlow/go-compliance side without art-dupl importing anything.

## RECONSIDER-WHEN (flip triggers)

1. art-dupl stops running under BuildFlow (loses covered-by-default status) — then `compliance.Record` (go-compliance/reporter.go:62) or a `CommandSource`/`FileSource` integration becomes the cheap compliance path; re-audit at that point.
2. go-compliance grows a **rule/policy engine** that can host blocking, AST-level, allowlist-bearing gates (i.e., something with jsonv2gate's expressiveness) — re-evaluate migrating the guards; until then the hub cannot express them.
3. The hub tags its own module and stabilizes a hub-embedding API, and the fleet wants an art-dupl-branded compliance view (e.g. clone-debt dashboard) — then adopt `hub`'s dashboard embed for that feature (still not a core dependency of the detector).
4. M26 (overview endgame: replace vs coexist) resolves and changes who owns fleet compliance — re-read ROADMAP and re-audit.

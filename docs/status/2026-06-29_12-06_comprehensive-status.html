Architectural reflections

Two-layer classification is subtle but correct

Per-clone ClassifyClone runs first (sets category, priority, suggestion), then group-level EvaluateActionabilityWithLabel overrides with pattern-specific labels. The idiom gate is a per-clone decision — correct. But the order dependency is implicit: if someone moves the idiom check after the actionability layer, the label override would clobber the idiom category. A comment at ProcessClones documenting this ordering contract would help.

printer/ magic numbers are policy, not domain

idiomTokenThreshold and idiomLineThreshold are unexported constants in printer/clone_classify.go. This is the correct location (classification policy), NOT domain. Domain types should not encode thresholds. No change needed — documenting the rationale.

07Top Question (g)

The one question I cannot figure out myself:

Should the idiom classification be a per-clone decision or a group-level decision?

Currently the idiom gate (<5 tokens AND ≤5 lines) runs in ClassifyClone — a per-clone function. But the group-level EvaluateActionabilityWithLabel can OVERRIDE the category via applyPatternLabel. This means: if a group of 3 clones each individually look like idioms (few tokens, few lines) but the group-level pattern matcher detects "interface-implementation", the label wins and the clone is marked non-actionable with a different suggestion. The ordering is correct today, but it's subtle.

Should we move the idiom gate after the actionability layer, so idioms are truly the last-resort classification? Or is per-clone correct because "idiom" is about the clone's own shape, independent of what pattern the group matches? I lean toward keeping it per-clone (current design) because the idiom category is fundamentally about the clone's size, not its group context — but I want your call.

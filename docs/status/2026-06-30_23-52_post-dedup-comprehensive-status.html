00Verdict

Production-shaped, fast, and well-tested — but two correctness landmines remain open under the hood. Build passes, lint is at zero, all 24 test-bearing packages are green, and harmful code duplication has been driven to zero this session. The surface API (7 output formats, 3 detection modes, SDK, baseline/CI) is complete and functional. The risks are concentrated in two architectural defects flagged as OPEN in AGENTS.md: destructive AST serialization that silently loses the Type-1-vs-Type-2 (renamed) distinction, and a non-concurrent-safe incremental cache-miss path. Neither blocks normal single-threaded use, but both are latent correctness/maintenance hazards.

05Totally Fucked Up (✅ all RESOLVED 2026-07-01)

Two correctness defects are flagged OPEN in AGENTS.md and confirmed against source. These are the real risks — they silently corrupt results under the right conditions rather than crashing loudly.

CRITICAL · ✅ RESOLVED (2026-07-01)

Destructive serialization breaks Type-2 classification

syntax.Serialize → serial() · printer/clone_processor.go::classifyCloneType

syntax.Serialize → serial() overwrites n.Type in place (fingerprintSubtree), so it is destructive on shared trees. Calling it twice double-hashes. Worse, classifyCloneType calls syntax.Serialize on nodes the suffix tree already serialized, and the walk short-circuits on Statement=true nodes — so the Type-1-vs-Type-2 (renamed) distinction is silently lost for statement-rooted fragments.

Impact: The clone-type badges in HTML/JSON output can be wrong for statement-rooted clones. Users relying on "Type 2 = renamed" to prioritize refactor work get silently incorrect data. No crash — just wrong labels.

Fix direction: Serialize into a side table, never mutate n.Type; walk node.Children directly for Name comparison. See docs/reviews/2026-06-30_18-31_full-code-review.html.
CRITICAL · ✅ RESOLVED (2026-07-01)

Incremental cache-miss aliasing (data race)

job/incremental.go · parseFile

The cache-miss path returns the same node slice it stores in the cache (the hit path correctly Clone()s). parseFile is not concurrent-safe, so under concurrent parse when multiple goroutines hit a fresh content-hash cache miss, they alias the same backing slice — a latent data race.

Impact: Only triggers on the incremental path with concurrent goroutines and a cache miss. Won't appear in single-threaded or all-cache-hit runs. But it is a genuine race that -race would flag.

Fix direction: Deep-clone-on-store + singleflight to deduplicate concurrent misses on the same key.

06What To Improve

1. Fix the two OPEN correctness defects first

They are the only things between the project and a clean "A". The destructive-serialization fix is the higher-leverage one — it makes clone-type labels trustworthy, which is the whole point of the semantic mode.

2. Non-destructive serialization as a foundation

The fix to (1) is also a prerequisite for safely caching serialized trees, reusing them across detection modes, and reasoning about the pipeline without "don't call it twice" footguns. It removes a whole class of "works only if called in the right order" bugs.

3. Decouple Printer from syntax.Node

Introduce the ProcessedClone DTO so actionability.go stops importing syntax.Node. This unblocks the printer/ package split and makes the printer testable in isolation.

4. Add tests to the 3 test-less packages

cmd/art-dupl (main binary), internal/testhelpers, and internal/testutil have zero test files. The main binary especially should have at least a smoke/integration test.

5. Run the test suite under -race in CI

The incremental cache aliasing defect (OPEN #2) is exactly the kind of bug -race catches. If nix flake check doesn't already run go test -race ./..., it should — it would have flagged this.

08The #1 Question I Cannot Answer Myself

BLOCKING DECISION

For the destructive-serialization fix: do we freeze the on-disk cache format, or accept a cache-busting version bump?

The correct fix for OPEN defect #1 is to stop mutating n.Type and serialize into a side table. But the current AST cache (cache/) gobs the serialized nodes including the mutated Type field, and the semantic encoding layout is [24-bit identifier/operator hash][8-bit base AST node type] packed into int32.

If I introduce a separate side table for fingerprints, there are two paths:

  • (A) Keep node.Type in the gob, add a parallel fingerprint map. Backwards-compatible cache, but now there are two sources of truth for the type field — a split-brain waiting to happen.
  • (B) Move the fingerprint out of node.Type entirely, bump the cache version. Clean single source of truth, but invalidates every existing baseline/cache file and requires a migration story for CI users with committed caches.

This is a one-way door for anyone who has committed cache files or baselines to their repo. I can't tell from the code alone whether external/CI consumers depend on the current cache format being stable, so I won't pick unilaterally. Which do you want: cache-format stability with a documented split-brain risk (A), or a clean format bump with a migration note (B)?

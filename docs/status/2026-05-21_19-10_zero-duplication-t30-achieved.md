## d) TOTALLY FUCKED UP

### 1. os.Exit Flaky Test Issue (CRITICAL BLOCKER)

**Packages:** `bdd/`, `cmd/`

**Symptom:** All 255 BDD specs show green (passing), all cmd test assertions pass, but test binary exits non-zero. Cobra calls `os.Exit()` during command execution; the in-process test runner catches this as failure.

**Impact:** CI always red for these 2 packages. Masks real test failures.

**Fix options:**
- (a) `cmd.SetExitFunc(func(int){})` in tests — suppress os.Exit
- (b) Subprocess-based testing for commands that exit
- (c) Refactor error handling to not call os.Exit in library code

## g) Top #1 Question I Cannot Figure Out Myself

**What is the intended relationship between `bdd/` and `cmd/` integration tests?**

Both test similar end-to-end scenarios. `bdd/` uses Ginkgo/Gomega with in-process Cobra execution. `cmd/` uses `testing` with `syscall.Dup2` for stdout capture. They overlap significantly.

Should we:
- **(a)** Merge — `bdd/` becomes single source of truth, delete redundant `cmd/` integration tests?
- **(b)** Keep separate — `cmd/` for unit-ish integration, `bdd/` for user-facing BDD scenarios?
- **(c)** Shared harness — refactor both to use common test infrastructure that solves os.Exit once?

This decision directly affects the os.Exit fix strategy and long-term test architecture.

## a) FULLY DONE

### Filter Override Bug (8 BDD failures → 0)

**Root cause chain (fully diagnosed):**

1. gogenfilter v3.1.0: `FilterDetailed(absolutePath)` silently errored because `os.DirFS(".")` rejects absolute paths
2. art-dupl's `shouldIncludeFile` returns `true` on filter errors → generated files were accidentally included by error-swallowing
3. gogenfilter v3.2.0 added `readFile()` fallback to `os.ReadFile` for absolute paths → filter now actually reads files
4. `FilterGeneric` (any "Code generated by" comment) catches sqlc/templ files even when `--include-sqlc` disables `FilterSQLC`
5. In v3.1.0 the error-swallowing masked this; in v3.2.0 the fix exposed the art-dupl logic bug

**Fix:** `generatorIncludes` policy in `cmd/util.go`:

- New `generatorIncludes` struct tracks which `--include-*` flags are active
- `shouldIncludeFile` overrides `FilterGeneric` when a file is caught by the generic catch-all but belongs to an explicitly-included category
- Content-only detection via `allowsContent(content []byte)` — bypasses gogenfilter's filename-gated `Is*Generated` functions (SQLC/templ/protobuf require filename match, but BDD test files use generic names)
- When includes are active, uses `FilterDetailedWithContent` (gogenfilter v3.2.0 API) — single content read, no double I/O
- When no includes active, falls back to two-phase `FilterDetailed` (filename check first, zero I/O for name-matched files)

## c) NOT STARTED

### Type Model Improvements (architecture follow-up, deferred)

- `syntax.Node.Pos`/`End` are `int32`; `domain.LineNumber` is `uint16`; printer `LineRangeMixin.StartLine` is `int` — three parallel position representations. `pkg/position/lines.go` already provides `ByteRangeToLines` but is not used as a canonical type.
- `config.DetectionMethods` wraps `[]DetectionMethod` with O(n) `Contains()` — fine for 2 methods, but a `map[DetectionMethod]struct{}` would be more idiomatic.
- Three parallel Clone DTOs: `domain.ProcessedCloneGroup`, `printer.CloneGroup`, `pkg/artdupl.Clone` — noted in AGENTS.md as "blocked on Printer/SDK DTO design".

### Performance: Multi-Read Content Pipeline

The crawl pipeline passes `chan string` (paths only). Content is read independently at:

1. Filter stage (`shouldIncludeFile` → `FilterDetailedWithContent`)
2. AST parse stage (`go/parser.ParseFile` or `os.ReadFile` for templ)
3. Incremental hash stage (`job/incremental.go:117`)
4. Clone result stage (`pkg/artdupl/detector_conversion.go:79,107`)

Worst case: 4 reads per file. Fixing this requires threading content through the pipeline — a significant refactor.

## e) WHAT WE SHOULD IMPROVE

1. **Consolidate Clone DTOs** — `domain.ProcessedCloneGroup`, `printer.CloneGroup`, `pkg/artdupl.Clone` should be unified into a single canonical type with format-specific views.

2. **Unify position types** — Extract a `Position` or `LineNumber` type in `pkg/position` and use it consistently across `syntax.Node` (`int32`), `domain` (`uint16`), and `printer` (`int`).

3. **Thread content through pipeline** — Pass `chan FileContent` instead of `chan string` through the crawl pipeline to eliminate redundant disk reads (currently up to 4x per file).

4. **`DetectionMethods` as set** — Change from `[]DetectionMethod` wrapper to `map[DetectionMethod]struct{}` for O(1) lookup.

5. **Push content-only detection upstream** — The `allowsContent` function in `cmd/util.go` uses hardcoded markers (`sqlcMarker`, `templMarker`, `protobufMarker`) because gogenfilter's `Is*Generated` functions are filename-gated for SQLC/templ/protobuf. Consider contributing content-only variants to gogenfilter.

6. **Consolidate config and SDK detection method enums** — Two parallel enum systems (`config.DetectionMethod` and `pkg/artdupl.DetectionMethod`) with conversion at the SDK boundary.

7. **Simplify `executeAnalysis` return type** — Returns `(chan syntax.Match, job.ParseStats, *FilterStats, error)`. Consider a callback-based API or a result struct.

8. **Audit `printer/html.go`** — 1484 lines, may have residual Finding references. Noted in AGENTS.md as overweight.
